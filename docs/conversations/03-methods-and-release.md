我读完了两个会话，并对照当前代码、研究笔记和原论文做了独立复核。你说的 **browsecamp 应该是 BrowseComp**。

**当前智能体结合的是：原子事实拆解、漏斗式检索、根据证据迭代补查、来源与支持度分开审查、引用绑定，以及搜索轨迹记录。** 其中一部分已经落实为代码，BrowseComp 等主要用于指导评测。

| 研究或方法 | 通俗原理 | 当前落实程度 |
|---|---|---|
| [FActScore](https://aclanthology.org/2023.emnlp-main.741/) | 把长回答拆成小事实，逐条检查 | **已借鉴**：最多拆出3条主张，保留对象、时间、版本和条件；没有计算正式 FActScore |
| [IRCoT](https://aclanthology.org/2023.acl-long.557/) | 根据已经查到的内容，决定下一步查什么 | **已借鉴**：检索→审查→发现缺口→生成补查；未复现论文的完整算法 |
| [TREC RAG](https://trec.nist.gov/pubs/trec34/papers/Overview_rag.pdf) | 分别检查关键事实覆盖和引用支持程度 | **支持度已落实**：FULL、PARTIAL、NONE，并增加矛盾和未知；完整 nugget 评分尚未落实 |
| [ALCE](https://aclanthology.org/2023.emnlp-main.398/) | 答案是否正确、引用是否支持答案，要分别检查 | **已落实部分机制**：回答绑定主张、原文与来源，检查逐字引用和位置；尚无正式 ALCE 跑分 |
| [STORM](https://github.com/stanford-oval/storm) | 从不同角度提问，并根据资料追问 | **架构启发**：直接查询、反证和补查；没有接入完整 STORM 专家对话流程 |
| [BrowseComp](https://openai.com/index/browsecomp/) | 用“难找、但容易核验”的问题测试搜索能力 | **调研与选题参考**，没有本项目的正式成绩 |
| [BrowseComp-Plus](https://texttron.github.io/BrowseComp-Plus/) | 固定语料、正例和困难负例，把检索能力与回答能力分开测 | **已有简易评分器**，尚未接入完整基准 |
| [LiveBrowseComp](https://arxiv.org/abs/2605.28721) | 检查模型是否真的依赖新证据，而不是凭记忆回答后补引用 | **设计参考**：开放问题先搜再提取事实；闭卷、删证据等对照实验尚未执行 |

FActScore、IRCoT、ALCE 属于基础研究；会话里讨论的较新方向，主要是 BrowseComp 系列与搜索轨迹诊断。

你提到的**漏斗搜索，当前确实有对应流程**：

```text
理解问题、拆出主张
→ 元宝搜索召回候选材料
→ 筛选并读取原文
→ 判断来源是否适用
→ 判断原文支持多少
→ 搜索反例、补齐缺口
→ 输出已查明内容和未查明事项
```

这里的“漏斗”是工作流组织方式。当前有逐步筛选和反馈补查，但完整实体消歧、证据图规划、学习式重排、信息增益优化还没有实现。默认限制是 **6次搜索、300秒调度预算、最多读取8页**。

**召回率也需要准确区分。** 当前代码已有：

> 指定来源召回率＝检出的必需参考来源数 ÷ 标注的必需参考来源总数。

它回答的是“该找到的材料有没有找到”；引用支持度回答的是“找到了以后，有没有正确使用”。2026年的[长程搜索诊断研究](https://arxiv.org/abs/2608.01913)也强调区分这两类失败。

不过，现在的评测仍是雏形：

- 主张覆盖率只比较编号，尚未验证事实内容是否完整。
- 来源采用率只检查引用关联，尚未等同于正确支持率。
- 搜索成功次数存在状态值不一致的问题。
- 既有三题属于演示验收，不能推出总体召回率、准确率或最佳模型排名。

所以，当前最准确的技术定位是：**借鉴上述研究、由元宝搜索和配置模型驱动的证据调查智能体，已经具备检索与核验闭环；公开基准评测仍待建设。** 六个角色代表工作职责，两道审查由同一配置模型分次执行。

## 8 · 助手 · final_answer

你可以把产品定位成：

> **一个以证据为中心、能主动寻找反例，并展示判断依据的搜索智能体。**

讲解时，重点讲下面这 **6个特点**，既有学术依据，也能对应实际功能。

| 可以讲的特点 | 学术表达 | 现场怎么解释 |
|---|---|---|
| **把问题拆小再查** | 原子主张分解，借鉴 FActScore | “一句话可能包含多个事实。我们把对象、时间、版本和条件拆开，分别核验，避免前半句正确、后半句是猜的。” |
| **根据查到的材料继续搜索** | 证据驱动的迭代检索，借鉴 IRCoT | “下一步搜索由已经找到的线索和缺口决定。例如发现某功能存在，但不知道是否支持离线，就专门补查离线条件。” |
| **逐层收窄材料** | 漏斗式检索与验证 | “先召回候选材料，再筛选来源、读取正文、核验主张，最后只让通过检查的内容进入回答。” |
| **来源与内容分开判断** | 来源适用性审查＋文本蕴含判断 | “官网也未必能证明这句话。我们分别判断：这个来源适不适合回答问题？这段原文究竟支持了什么？” |
| **区分完整支持和部分支持** | 细粒度证据归因，参考 TREC RAG、ALCE | “原文只说‘支持导出’，系统就不能顺便回答‘支持离线导出’。相关材料、部分支持和完整支持是不同状态。” |
| **主动找反例，并保留完整记录** | 反证检索、冲突检查与证据溯源 | “形成初步判断后，还会查限制、例外和不同说法。每条结论能追溯到实际查询、来源和原文片段。” |

**最值得强调的技术特色，是“模型判断＋程序校验”。**

模型负责理解来源、判断文字支持程度；程序负责检查引用是否确实来自取得的材料、是否绑定正确的主张，以及证据是否达到输出门槛。这样，判断过程有可检查的约束。

你还可以讲一个研究视角：

> **我们区分两种失败：没有找到必要证据，以及找到了证据却没有正确利用。**  
> 前者需要改善查询和召回，后者需要改善阅读、证据选择和归因。记录搜索轨迹，就是为了知道问题发生在哪一步。

这比单独展示“搜了多少次、返回多少网页”更有解释力。

你可以直接使用下面这段约一分钟的介绍：

> 我们做的是一个可审计的证据调查智能体。用户提出问题后，它先把问题拆成可以分别核验的小主张，再通过元宝搜索寻找材料。  
>   
> 整个过程采用漏斗式工作流：从候选召回，到读取原文，再分别审查来源是否适用、原文是否完整支持主张。发现缺失条件后，会继续补查，并主动寻找限制和反例。  
>   
> 方法上，我们借鉴了 FActScore 的原子事实思想、IRCoT 的迭代检索思想，以及 TREC RAG、ALCE 的引用支持评估。每条确定回答都绑定具体证据，用户可以查看它实际查了什么，以及结论依据在哪里。

**介绍研究关系时用“借鉴”，介绍产品能力时用“实现了哪些机制”。** BrowseComp 可以说是评测设计参考；目前不要说已经取得其跑分，也不要报总体准确率、召回率或“六个独立模型互相验证”。
