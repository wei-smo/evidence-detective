## 我查到的开源框架

### 1. STORM：最值得借鉴调查逻辑

[Stanford STORM](https://github.com/stanford-oval/storm) 的核心思路很适合你：

- 先发现不同调查视角；
- 再围绕这些视角提出问题；
- 多轮搜索收集资料；
- 最后生成带引用的报告；
- 检索器可以替换。

你可以借鉴它的“多视角调查”：

比如用户问：

> 这个软件功能真的支持国产系统吗？

系统不要只搜一句，而是拆成：

- 官方文档是否支持；
- 官方发行说明什么时候加入；
- 用户实际使用情况如何；
- 是否有版本限制；
- 是否存在不支持的硬件或系统；
- 有没有官方替代方案。

STORM 更适合做知识整理和长报告，你的比赛作品应该把它改造成更快、更直观的“证据卡片”。

### 2. GPT Researcher：最适合借鉴检索器接口

[GPT Researcher](https://github.com/assafelovic/gpt-researcher) 的优势是把“研究流程”和“搜索引擎”分开。

它支持：

- 不同搜索引擎；
- 自定义 Retriever；
- MCP 数据源；
- 多智能体研究；
- 带引用的研究报告。

你可以只借鉴它的接口思想，自己写一个：

```python
class YuanbaoRetriever:
    async def search(self, query: str) -> list[Source]:
        ...
```

把元宝搜索返回的字段统一成内部结构：

```python
class Source:
    title: str
    url: str
    passage: str
    content: str
    site: str
    date: str
    score: float
    source_type: str
```

这样以后即使换搜索服务，也不用改整个智能体。

### 3. DeerFlow：最适合借鉴工具扩展机制

[ByteDance DeerFlow](https://github.com/bytedance/deer-flow) 是更完整的 SuperAgent 框架，支持：

- 子智能体；
- 网页搜索；
- 网页抓取；
- 沙箱；
- 记忆；
- MCP；
- 自定义工具；
- 长流程任务。

比较关键的是，它当前主线已经包含了 Tencent WSA，也就是腾讯云 Web Search API 的搜索工具适配。元宝搜索本质上使用的就是腾讯云这套搜索接口，因此接入方式是兼容的。

但是我不建议你现在完整部署 DeerFlow。原因很简单：它太重，比赛时间应该优先花在“场景差异”和“演示效果”上，而不是处理 Docker、依赖、模型配置和部署问题。

### 4. LangGraph：如果你想做状态机

[LangGraph](https://github.com/langchain-ai/langgraph) 适合把调查过程写成一个有状态工作流：

```text
问题输入
  ↓
主张提取
  ↓
调查计划
  ↓
元宝搜索
  ↓
证据整理
  ↓
冲突检测
  ↓
结论生成
  ↓
人工复核
```

它适合长期产品，但你这次比赛也可以不用它，直接用 Python 或 TypeScript 写一个轻量流程。核心不在于用了哪个框架，而在于搜索是否真的改变了结果。

另外，LangChain 的 `open_deep_research` 仓库目前已经归档，所以不建议把它作为长期主框架；可以拿来参考流程，但不建议直接基于它搭新项目。

## 最容易让你脱颖而出的地方

比赛规则里，侦探赛道重点看：

- 完成度和可用性：30%
- 创意：25%
- 场景价值：25%
- 展示：20%

所以最优策略不是堆十几个功能，而是做出一条评委一看就懂的完整链路。

### 第一差异：证据卡，而不是聊天答案

普通搜索结果是：

> 这个说法大概率是真的。

你的产品应该展示：

```text
结论：部分成立

支持证据：
[1] 官方公告：确认活动时间为 10 月 25 日
[2] 官方购票页：仍显示部分票档可购买

反驳或限制：
[3] 主办方微博：VIP 票已售罄
[4] 第三方文章：发布时间早于官方公告

缺失信息：
- 普通票实时库存无法确认
- 需要用户点击购票页最终确认
```

评委可以看到：

- 你搜索了什么；
- 为什么搜索；
- 哪个来源支持结论；
- 哪个来源与它冲突；
- 系统为什么没有强行下结论。

这比“回答更聪明”更容易让评委信服。

### 第二差异：主动寻找反证

大多数搜索智能体只会搜支持自己答案的内容。

你要明确加入一个步骤：

```text
寻找支持证据
+
寻找反证
+
检查时间和适用条件
```

例如用户问：

> 这个活动还可以买票吗？

系统不能只搜“活动购票”，还应该搜索：

- 活动官方公告；
- 票务平台当前状态；
- “售罄、延期、取消、变更”；
- 日期、城市和票种；
- 官方账号的最新通知。

这会形成明显的“侦探感”。

### 第三差异：把“未知”做成产品能力

最容易赢得信任的不是每次都回答，而是明确告诉用户：

```text
目前不能确认

已找到：
- 2026 年 10 月 20 日的官方公告
- 2026 年 10 月 22 日的媒体报道

仍缺少：
- 2026 年 10 月 24 日的实时状态

建议：
点击官方页面确认当前状态
```

比赛题目明确强调“查不到敢说不知道”。这应该成为你的核心产品能力，而不是错误处理里的一个小提示。

### 第四差异：显示“为什么停止搜索”

不要只显示一个加载动画。

可以显示调查时间线：

```text
14:32 识别出 3 个待核实主张
14:32 搜索官方来源
14:33 搜索反方关键词
14:33 发现 2 个来源存在时间冲突
14:34 补查最新公告
14:34 关键结论已有 2 个独立来源，停止搜索
```

这会让评委感受到它是“会调查的智能体”，而不是后台偷偷调用一次 API。

## 我建议的具体比赛场景

不要做“万能搜索助手”。最好选择一个窄而真实、但普通搜索容易出错的场景。

我建议优先考虑这三个方向：

### 方向一：公开信息事实核查

例如：

- 家族群传言真假；
- 社交媒体上的产品说法；
- 某个政策是否真的发布；
- 某条新闻是否过时；
- 某产品功能是否真的存在。

优点是最容易展示“支持、反驳、未知”。

### 方向二：活动和出行状态核查

例如：

- 演唱会是否延期；
- 某展览是否还开放；
- 是否需要预约；
- 票是否仍可买；
- 活动地点是否发生变化。

优点是用户行动明确：查完以后要不要去、要不要买票、要不要预约。

### 方向三：软件和产品版本侦探

例如：

> 某个功能到底从哪个版本开始支持？Windows、macOS、Linux 是否一致？官方文档和用户文章为什么说法不同？

这个方向比较适合技术人群，也容易利用官方文档、发行说明、GitHub Issue 和用户反馈形成证据链。

如果目标是比赛现场效果，我更推荐：

> “公开信息事实核查 + 产品/活动状态确认”的证据侦探。

不要一开始就限定成纯谣言检测，因为“谣言”容易涉及政治、个人和敏感内容。比赛规则本身也明确不碰时政和个人消息。

## 最少要做的 MVP

第一版只做以下功能：

### 输入区

用户输入：

```text
我看到一个说法，帮我查清楚：
“某软件已经支持 XX 功能，而且所有版本都能用。”
```

### 调查计划区

系统显示：

```text
本次调查将核实：

1. 该功能是否真的存在
2. 从哪个版本开始支持
3. 哪些系统支持
4. 是否存在限制条件
5. 是否有相反证据
```

### 调查过程区

显示：

- 当前检索词；
- 查询轮次；
- 找到了多少来源；
- 是否发现冲突；
- 当前是否继续搜索。

### 结果区

显示：

- 总结论；
- 可信程度；
- 支持证据；
- 反驳证据；
- 冲突来源；
- 尚未确认的内容；
- 下一步建议。

### 来源区

每条来源至少显示：

- 标题；
- 网站；
- 日期；
- 摘要；
- 来源等级；
- 可点击 URL；
- 它支持哪条结论。

## 三个演示案例应该这样准备

建议提前准备三类案例：

### 案例 1：普通问题

能快速找到官方来源，最终结论明确。

### 案例 2：冲突问题

不同网页说法不一致，系统通过日期、版本或适用对象解释冲突。

### 案例 3：资料不足

搜索很多次仍无法确认，系统明确输出“证据不足”，而不是编一个答案。

第三个案例很重要，因为它直接展示你的产品和普通 AI 问答的区别。

## 开发优先级

按照比赛时间，建议这样排：

1. 元宝搜索适配器；
2. 一次搜索到结果的完整网页；
3. 证据卡和可点击来源；
4. 问题拆解；
5. 支持/反驳/未知判断；
6. 冲突检测；
7. 调查时间线；
8. 最后再考虑截图查证或持续盯梢。

暂时不要优先做：

- 多模型切换；
- 复杂记忆；
- 用户登录；
- 向量数据库；
- 多租户；
- 完整 DeerFlow 部署；
- 复杂后台；
- 一堆不影响演示的设置项。

# 一、怎样判断一个搜索基准是否可靠

## 1. 先区分五种有效性

一个基准是否可靠，至少要检查以下五个维度。

### 第一，构念有效性

它到底测的是搜索能力，还是模型记忆能力？

例如：

```text
题目：谁在 2020 年获得某奖项？
```

如果模型训练语料中已经有明确答案，那么它可能不搜索也能答对。

更好的题目是：

```text
请找出某个小众组织在最近一次公告中提到的三个合作方，并说明每个合作方对应的项目。
```

这类问题：

- 信息分散；
- 需要多次搜索；
- 需要实体消歧；
- 依赖网页中的新内容；
- 不能只靠模型记忆完成。

这正是 BrowseComp 和 LiveBrowseComp 的差异。静态基准适合测试浏览能力，实时新鲜事实基准更适合测试“是否真的依赖外部搜索”。([arxiv.org](https://arxiv.org/abs/2504.12516))

### 第二，证据有效性

每一道题都必须知道：

- 哪些网页或段落支持答案；
- 哪些网页反驳答案；
- 哪些网页只是相关但不能证明；
- 哪些网页是旧版本；
- 哪些网页是转载；
- 哪些证据是必需的；
- 哪些证据只是辅助的。

不能只保存一个参考答案。

不可靠的基准：

```json
{
  "question": "问题",
  "answer": "答案"
}
```

可靠的基准：

```json
{
  "question": "问题",
  "answer_schema": "entity_set",
  "gold_claims": [
    {
      "claim_id": "C1",
      "text": "对象 A 在时间 T 具备能力 X"
    }
  ],
  "gold_evidence": [
    {
      "evidence_id": "E1",
      "claim_id": "C1",
      "url": "https://example.com/page",
      "quote": "原文中的连续片段",
      "label": "support",
      "required": true
    }
  ],
  "counter_evidence": [],
  "acceptable_answers": [],
  "unknown_allowed": true
}
```

### 第三，评测者有效性

不能只用一个大模型判断“回答得好不好”。

建议采用三级评估：

```text
程序硬评估
    ↓
证据与主张自动对齐
    ↓
人工抽样复核
```

程序可以检查：

- URL 是否真实存在；
- 引用片段是否确实出现在页面中；
- 搜索结果是否真的返回过该 URL；
- 引用是否绑定了正确主张；
- 查询次数和预算是否超限；
- 答案实体集合是否有遗漏。

模型评审可以辅助判断：

- 证据是否蕴含结论；
- 结论是否偷换对象；
- 是否误读时间和版本；
- 是否存在未解释冲突。

人工复核必须覆盖：

- 高分样本；
- 低分样本；
- “最终答对但引用错误”的样本；
- “证据充分但模型答错”的样本；
- “证据不足却输出确定答案”的样本。

### 第四，重现性

同一个智能体多跑几次，结果是否大致稳定？

至少要报告：

- 多次运行平均分；
- 标准差；
- 成功率置信区间；
- 平均搜索次数；
- P50、P90 延迟；
- 不同结果排序下的性能；
- 不同提示词下的性能；
- 不同时间点下的性能。

如果一个模型在 100 道题上得分 60%，但不同随机种子之间在 45%—75% 波动，那么“60%”本身并不可靠。

### 第五，外部有效性

基准是否只适合某个搜索引擎、某种网页模板或某个模型？

需要做这些拆分：

- 训练域与测试域分离；
- 网站来源分离；
- 时间分离；
- 问题模板分离；
- 搜索引擎分离；
- 语言分离；
- 页面结构分离。

否则模型可能学到：

```text
看到这种题型 → 搜这个固定关键词 → 打开固定网站
```

这不是搜索智能，而是模板记忆。

# 二、把问答任务转化为开放检索任务

你提到的“漏斗检索”非常重要。

普通问答是：

```text
问题 → 答案
```

Agentic Search 更适合建模为：

```text
问题
  ↓
主张拆解
  ↓
候选线索召回
  ↓
实体消歧
  ↓
局部证据核验
  ↓
反证与冲突搜索
  ↓
补齐答案集合
  ↓
停止判断
  ↓
最终回答
```

这就是一个搜索漏斗。

## 1. 第一层：问题理解

把用户问题拆成：

- 目标实体；
- 目标属性；
- 时间范围；
- 地区；
- 版本；
- 数量要求；
- 是否要求全集；
- 是否允许“不知道”。

例如：

> 2026 年某软件是否支持离线导出？哪些版本支持？有没有限制？

应该变成：

```text
C1：软件是否支持离线导出？
C2：从哪个版本开始支持？
C3：哪些系统或版本支持？
C4：是否存在格式、权限或网络限制？
C5：是否存在旧版本不支持的反例？
```

## 2. 第二层：宽召回

宽召回阶段允许查询比较宽：

```text
软件名 离线导出
软件名 离线导出 官方
软件名 离线导出 版本
软件名 离线导出 限制
```

这里的目标不是马上回答，而是找到：

- 可能的官方页面；
- 版本号；
- 相关产品名；
- 关键术语；
- 可能存在的反例。

## 3. 第三层：线索扩展

把已经找到的实体和术语加入新查询：

```text
软件名 3.4 离线导出
软件名 release notes offline export
软件名 permissions offline export
软件名 export PDF version
```

这里是搜索智能体和普通 RAG 的重要区别：后续查询应该由前面找到的证据驱动，而不是永远围绕原问题改写。

## 4. 第四层：证据核验

对每个候选来源判断：

- 是否真的涉及目标对象；
- 是否满足目标时间；
- 是否满足目标版本；
- 是否是原始来源；
- 是否只是转载；
- 是否支持完整主张，还是只支持其中一半。

## 5. 第五层：反证检索

每一个确定结论都应该主动寻找反证：

```text
对象 + 不支持 + 功能
对象 + 限制
对象 + 旧版本
对象 + 已移除
对象 + bug
对象 + 官方更正
```

不能只搜索支持结论的内容。

## 6. 第六层：停止判断

停止条件不应该是“已经搜索了 6 次”，而应该是：

```text
所有必要主张都有证据
+
没有未解释的关键冲突
+
新增搜索不再带来新的实体、属性或证据
```

也可以定义一个证据饱和指标：

```text
新增证据收益(t)
= 第 t 次搜索发现的新增必要证据数
```

如果连续两次搜索：

```text
新增必要证据数 = 0
```

并且所有主张已经达到最低证据门槛，就可以停止。

# 三、元宝搜索应该标注什么数据

元宝搜索返回的是搜索结果，不等于已经验证的事实。因此建议在自己的系统中建立一层标注，不要直接把元宝返回的 `score` 当成事实可信度。

## 1. 页面级标注

每个搜索结果至少记录：

```json
{
  "source_id": "S12",
  "url": "https://example.com/page",
  "title": "页面标题",
  "domain": "example.com",
  "site": "网站名称",
  "date": "页面日期",
  "retrieved_at": "检索时间",
  "yuanbao_score": 0.82,
  "page_status": "accessible",
  "source_type": "official|primary|media|forum|repost|unknown",
  "freshness": "current|stale|unknown",
  "publisher_group": "example.com",
  "independence_group": "content-cluster-7"
}
```

`yuanbao_score` 表示搜索引擎相关性排序分数，不应直接解释成：

```text
0.82 = 82% 可信
```

## 2. 证据级标注

对页面中的具体段落进行标注：

```json
{
  "evidence_id": "E12",
  "source_id": "S12",
  "claim_id": "C3",
  "quote": "连续原文片段",
  "relevance": 3,
  "entailment": "support",
  "strength": "direct",
  "polarity": "positive",
  "time_match": true,
  "entity_match": true,
  "condition_match": false,
  "required": true
}
```

推荐把相关性分为四级：

```text
0 = 无关
1 = 主题相关，但不能帮助回答
2 = 部分相关，支持某个子问题
3 = 直接回答关键主张
```

推荐把证据关系分为：

```text
support       直接支持
counter       直接反驳或提供反例
context       提供背景，但不能证明主张
stale         旧信息
duplicate     转载或重复
ambiguous     对象/版本/时间不明确
misleading    标题相关但正文不支持
```

## 3. 正例、反例和干扰例

### 正例

正例不是“包含关键词的页面”，而是：

```text
页面内容直接蕴含目标主张
```

### 反例

反例包括：

- 明确否定；
- 限制条件；
- 旧版本不支持；
- 某地区不适用；
- 某个真实反例推翻全称命题；
- 官方更正。

### 干扰例

干扰例尤其重要：

- 标题相似但正文无关；
- 内容相同但只是转载；
- 页面已经过时；
- 对象名称相同但不是同一个实体；
- 只描述相关功能，不描述目标功能；
- 搜索摘要支持，但打开正文后不支持。

如果没有负例和干扰例，模型会学成：

```text
关键词匹配 = 证据
```

而不是：

```text
证据蕴含 = 支持
```

# 四、召回率应该怎样定义

这里至少要拆成四种召回率。

## 1. 页面召回率

搜索结果中是否找到了所有必要来源：

```text
Required Source Recall
= 找到的必要来源数 / 标注的必要来源总数
```

例如标注了 4 个必要来源，智能体找到 3 个：

```text
3 / 4 = 75%
```

## 2. 证据段落召回率

页面找到了，但关键段落没有被读取，也不能算真正召回：

```text
Evidence Recall
= 找到的必要证据段落数 / 必要证据段落总数
```

## 3. 主张覆盖率

```text
Claim Coverage
= 有至少一个有效证据的关键主张数 / 关键主张总数
```

例如一个问题有 5 个子主张，只有 4 个被有效覆盖：

```text
4 / 5 = 80%
```

## 4. 答案集合召回率

适合“找出所有符合条件的对象”：

```text
Answer Set Recall
= 正确找出的目标实体数 / 标准答案实体数
```

同时要计算：

```text
Answer Set Precision
= 找出的正确实体数 / 智能体输出的实体总数
```

否则模型可以通过输出一大堆候选来伪造高召回。

## 5. 证据利用率

这是搜索智能体特别重要的指标：

```text
Evidence Utilization
= 被最终答案正确使用的必要证据数 / 已经检索到的必要证据数
```

它能区分两种失败：

```text
检索缺口：
必要证据根本没有找到。

利用缺口：
必要证据找到了，但模型没有读懂、没有引用或没有用于结论。
```

这两个问题的修复方式完全不同。

# 五、每轮搜索应该记录什么

建议每个 agent turn 记录以下结构：

```json
{
  "task_id": "task-001",
  "run_id": "run-abc",
  "turn": 3,
  "state": {
    "active_claims": ["C2", "C4"],
    "known_entities": ["软件名", "版本 3.4"],
    "unresolved_gaps": ["系统兼容性"]
  },
  "action": {
    "type": "search",
    "query": "软件名 3.4 Linux 离线导出",
    "purpose": "resolve_version_constraint"
  },
  "yuanbao": {
    "request_id": "xxx",
    "result_count": 10,

  },

    "opened_sources": ["S14"],
```

特别注意区分：

```text

智能体实际引用了什么
```

很多系统把这五层混成一个“检索结果”，导致无法定位问题。

# 六、搜索调用次数该如何评价

搜索调用次数本身不是越少越好，也不是越多越好。

应该报告：

- 平均调用次数；
- 中位数；
- P90；
- 每题最大调用次数；
- 每次调用延迟；
- 每次调用新增证据；
- 第一次发现关键证据所需调用数；
- 达到充分证据后又调用了多少次；
- 因接口错误重复调用多少次。

推荐几个指标：

## 1. 单次搜索证据收益

```text
Evidence Yield
= 新增必要证据数 / 搜索调用次数
```

## 2. 任务成功效率

```text
Search Efficiency
= 任务成功率 / 平均搜索调用次数
```

## 3. 证据召回效率

```text
Recall Efficiency
= 必要证据召回率 / 平均搜索调用次数
```

## 4. 过度搜索比例

```text
Over-search Ratio
= 达到证据门槛后多余调用数 / 总调用数
```

## 5. 有效搜索率

```text
Useful Search Rate
= 带来新实体、新属性、新必要证据或关闭冲突的调用数
  / 总调用数
```

你真正想优化的不是：

```text
搜索次数最多的模型
```

而是：

```text
在相同搜索预算下，证据召回和任务成功最高的模型
```

# 七、如何创建可靠的训练数据

REDSearcher 的思路很值得借鉴：不是随机制造复杂问题，而是用证据图的拓扑复杂度和证据分散度来控制任务难度，并同时设计任务合成、中间训练和后训练流程。论文还强调，搜索轨迹和高质量奖励非常稀缺，因此需要低成本模拟环境和严格过滤。([arxiv.org](https://arxiv.org/abs/2602.14234))

## 1. 从证据图开始

把资料库构造成：

```text
问题
  ↓
子主张
  ↓
实体/关系
  ↓
网页
  ↓
段落
  ↓
可验证结论
```

控制难度的变量包括：

- 跳数；
- 证据分散程度；
- 需要满足的条件数量；
- 干扰页面比例；
- 反例数量；
- 来源冲突数量；
- 页面深度；
- 时间新鲜度；
- 答案集合大小。

例如：

```text
简单：
一个页面支持一个主张。

中等：
两个页面分别支持两个子主张。

困难：
三个页面支持三个子主张，另外有一个旧页面和一个反例页面。

很难：
需要从四个网站中找出实体链，最后还要判断哪个版本有效。
```

## 2. 同一个问题生成多种轨迹

不要只生成“成功轨迹”。

至少要生成：

```text
A. 高质量成功轨迹
B. 答对但证据错误轨迹
C. 找到证据但没有使用轨迹
D. 过早停止轨迹
E. 无限搜索轨迹
F. 查询循环轨迹
G. 被干扰页面误导轨迹
H. 工具报错后恢复轨迹
I. 找不到证据并正确拒答轨迹
```

这些轨迹对训练搜索智能体比单纯的正确答案更有价值。

## 3. 训练数据过滤级联

推荐这样过滤：

```text
格式可执行
  ↓
网页真实存在
  ↓
证据确实支持主张
  ↓
答案与证据一致
  ↓
搜索轨迹有目标
  ↓
没有无效循环
  ↓
多个独立验证器一致
  ↓
人工抽检
```

不要只让一个大模型说“这条轨迹很好”。

## 4. 训练顺序

推荐：

```text
第一阶段：工具格式和搜索调用训练
第二阶段：高质量轨迹 SFT
第三阶段：轨迹偏好训练
第四阶段：真实环境 RL
第五阶段：困难样本挖掘
```

关于奖励设计，最新实证研究的结论很重要：格式奖励通常有效；中间检索奖励的收益并不稳定；基础模型规模和初始化方式会影响 RL；搜索引擎本身也会改变训练动态和部署鲁棒性。([arxiv.org](https://arxiv.org/abs/2505.15117))

因此不要一开始设计十几个奖励：

```text
搜索一次 +1
找到一个结果 +1
写一个 query +1
```

这很容易把模型训练成：

```text
为了拿奖励而搜索
```

更合理的主奖励是：

```text
最终任务成功
+
证据支持正确
+
必要主张完整
+
未知时诚实拒答
-
无效搜索成本
-
错误引用
-
过度断言
```

# 八、为什么搜索轨迹是关键

## 1. 最终答案是欠定的

同一个正确答案可能来自：

```text
真正找到并理解了证据
靠模型记忆猜中
看到错误页面但碰巧输出正确
搜索很多次后随机选中
```

只看最终答案无法区分这些情况。

## 2. 轨迹可以做信用分配

你需要知道：

- 哪个查询找到了关键实体；
- 哪个页面带来了决定性证据；
- 哪个步骤导致错误分支；
- 哪一次调用只是重复；
- 哪次反证搜索改变了结论；
- 哪一步本应继续搜索却提前停止。

这对训练 critic、构造偏好数据和改搜索策略都非常重要。

## 3. 轨迹可以识别具体行为趋势

### 趋势一：记忆依赖

做三个实验：

```text
闭卷
正常搜索
删除支持证据后的搜索
```

如果：

```text
闭卷也很高
删除证据后仍然自信答对
```

说明模型可能是在用搜索确认已有答案，而不是发现答案。LiveBrowseComp 把这种现象定义为 Intrinsic Knowledge Dependence。([arxiv.org](https://arxiv.org/abs/2605.28721))

### 趋势二：查询循环

记录：

```text
语义重复查询率
连续无新增信息步数
重复访问 URL 数
每步新增实体数
每步新增必要证据数
```

如果搜索次数不断增加，但新证据为零，就是循环或停止策略失败。

### 趋势三：检索缺口与利用缺口

分别统计：

```text
必要证据未被召回
必要证据已召回但未被使用
```

前者要改查询和召回，后者要改重排、页面阅读和证据绑定。

### 趋势四：确认偏误

记录模型是否：

- 只搜索支持自己的词；
- 遇到反例后是否改变结论；
- 是否主动搜索“不支持、限制、取消、旧版本”等词；
- 是否把转载数量当成独立证据；
- 是否忽略时间和版本差异。

### 趋势五：过早停止与过度搜索

绘制：

```text
步骤数 → 必要证据覆盖率
步骤数 → 任务成功概率
步骤数 → 新增证据收益
```

可以看到：

- 证据还不完整就停止；
- 证据已经饱和还继续搜索；
- 搜索很多但没有信息增益；
- 关键证据早已出现却没有被利用。

每道题至少标注：


# 十、模型和元宝搜索如何比较

你之前问“哪个模型配合元宝搜索搜索率最高”，我建议不要把“搜索率最高”定义为调用次数最高。

应该比较这几个指标：

| 指标 | 含义 |
|---|---|
| Search Activation Rate | 需要搜索的题目中，模型实际调用搜索的比例 |
| Live Accuracy | 开放实时环境中的答案正确率 |
| Evidence Recall | 必要证据召回率 |
| Evidence Utilization | 找到的证据被正确使用的比例 |
| Citation Precision | 引用真正支持结论的比例 |
| Search Calls | 平均搜索调用次数 |
| Useful Search Rate | 带来新证据的调用比例 |
| Time to Evidence | 找到关键证据所需时间 |
| Cost per Success | 每个成功任务的搜索与推理成本 |
| Abstention Quality | 无证据时是否正确拒答 |

最终可以定义：

```text
Search Efficiency Score
= 任务成功率 × 证据召回率 × 引用精度
  / 平均搜索调用次数
```

模型对比必须固定：

- 同一元宝搜索接口；
- 同一题集；
- 同一搜索结果数量；
- 同一最大调用预算；
- 同一系统提示词；
- 同一超时时间；
- 同一页面读取规则；
- 同一评测器；
- 多次随机重复。

模型端口建议统一为兼容接口：

```text
REASONING_BASE_URL
REASONING_API_KEY
REASONING_MODEL
```

然后用配置切换模型：

```text
MODEL_A
MODEL_B
MODEL_C
```

对每个模型运行：

```text
闭卷基线
一次搜索基线
多轮搜索智能体
证据删除测试
实时新鲜测试
干扰页面测试
```

目前不能凭模型名称直接判断哪个 OpenAI 模型和元宝搜索组合最好。因为最新研究已经显示，模型规模、初始化方式和搜索引擎本身都会显著影响搜索智能体训练与部署结果；某个模型在闭卷任务上强，不代表它在实时开放检索中搜索效率最高。([arxiv.org](https://arxiv.org/abs/2505.15117))

你真正要找的不是：

> 谁搜索调用最多？

而是：

> 谁能在相同元宝搜索预算下，用更少的调用找到更多必要证据，并且正确使用这些证据？

# 最终推荐的评估架构

```text
Benchmark Manager
    ├── Frozen Yuanbao Replay
    ├── Live Yuanbao Search
    ├── Evidence Graph
    ├── Positive / Counter / Distractor Labels
    ├── Agent Trajectory Logger
    ├── Claim-Evidence Grader
    ├── Recall / Precision / Coverage
    ├── Cost / Latency / Search Budget
    └── Model Comparison Report
```

最关键的三个结论是：

1. BrowseComp 解决“能不能找到难找事实”，但必须增加 LiveBrowseComp 式的新鲜事实测试，防止模型靠记忆验证。([arxiv.org](https://arxiv.org/abs/2504.12516))

2. 基准的 gold 标注不能只有答案，必须包含证据图、支持/反例、相关性、时间、来源独立性和未知标签。

3. 搜索轨迹不是日志附属物，而是训练和诊断的核心数据。它能区分“没搜到”“搜到了没用”“错误确认”“过早停止”和“无效循环”。

```text
   ↓

   ↓

```

每一层都要单独评估，不能用一个总分代替。

## 一、先区分四个概念

### 1. 来源可靠性

这个来源本身是否适合承担某类判断？

例如：

- 软件官方文档适合回答“官方是否支持某功能”；
- 用户论坛适合回答“用户实际遇到了什么问题”；
- 媒体报道适合提供事件线索；
- 营销页面可能适合证明“厂商宣称了什么”，但不一定适合证明真实性能；
- 搜索摘要只能作为线索，不能自动当作原文证据。

### 2. 来源相关性

这个来源是否和当前问题有关？

相关不等于支持。

例如一篇文章标题是：

> 某软件新增 PDF 导出功能

它和“软件是否支持离线 PDF 导出”相关，但文章可能完全没有说明“离线”，因此只能算部分相关。

### 3. 归因支持度

引用的具体文本是否真正支持答案中的陈述？

这是你说的“支持度”或“attribution”。

### 4. Nugget 完整性

答案是否覆盖了用户真正需要的关键事实单元？

比如用户问：

> 软件从哪个版本开始支持 PDF 离线导出？哪些系统支持？是否需要联网？

它不是一个事实，而是至少四个 nuggets：

```text
N1：是否支持 PDF 导出
N2：是否支持离线导出
N3：从哪个版本开始支持
N4：哪些系统支持
N5：是否需要联网
```

一个答案可能对 N1、N3 有证据，但完全没有回答 N4、N5。它不能被评价为“完整正确”。

# 二、来源可靠性不能用一个全局分数

我不建议给域名设置永久权重，例如：

```text
example.com = 0.9
forum.com = 0.4
```

更合理的是评估：

```text
R(source | claim, time, version, region)
```

也就是说：

> 一个来源对于某一个具体主张、时间、版本和地区是否可靠。

同一个来源在不同任务中的证据能力可能不同。

例如厂商官网：

```text
回答官方产品功能：强
回答用户实际体验：中
回答产品是否真的比竞品快：弱
回答历史版本问题：取决于是否有版本档案
```

## 推荐的来源评估维度

每个来源都标注：

```json
{
  "identity": "clear",
  "source_type": "official|primary|secondary|forum|repost|unknown",
  "primaryness": "primary",
  "entity_match": "yes",
  "time_match": "yes",
  "version_match": "partial",
  "jurisdiction_match": "yes",
  "freshness": "current",
  "independence_group": "vendor-official",
  "correction_history": "unknown",
  "conflict_of_interest": "interested_party"
}
```

具体包括：

- 发布者身份是否明确；
- 是否一手来源；
- 对象是否匹配；
- 时间是否匹配；
- 版本是否匹配；
- 地区或适用范围是否匹配；
- 是否为当前有效信息；
- 是否是转载；
- 是否存在更正、撤回或版本变更；
- 是否存在明显利益关系；
- 页面是否可稳定访问；
- 是否能提供完整上下文。

## 建议的离散可靠性等级

不要一开始伪造一个 `0.873` 这样的精确可靠性概率。先使用可解释等级：

```text
R3：任务适用的一手材料，身份、时间、对象和范围清楚

R2：可信的二手材料，或能够被多个独立来源交叉验证

R1：有相关性，但身份、时效、条件或独立性存在问题

R0：仅作搜索线索，不能单独支撑结论
```

注意：

> R3 不等于“这个来源一定是真实的”。  
> R3 表示“它具备承担该类证据的条件”。

这很重要。官方营销页也可能是 R3 的“厂商声明证据”，但不是客观性能证据。

# 三、评判智能体应该评估来源，但不能单独决定真相

可以让一个专门的 Source Judge 判断来源是否适合使用，但不能让同一个生成答案的模型自己给自己的来源打分。

更可靠的流程是：

```text
搜索结果
  ↓
规则检查
  - URL 是否可访问
  - 页面是否真实返回
  - 时间和版本是否匹配
  - 是否重复转载
  ↓
来源评判智能体
  - 身份
  - 一手性
  - 适用范围
  - 时效性
  ↓
证据支持评判智能体
  - 是否支持主张
  - 支持全部还是一部分
  ↓
人工抽样校准
```

来源评估和主张支持度评估最好拆成两个 judge：

```text
Source Applicability Judge
判断：这个来源适不适合用？

Claim-Evidence Judge
判断：这段证据支持不支持这个主张？
```

否则容易出现一种错误：

> 因为来源看起来权威，所以模型自动判定它支持答案。

来源权威和文本蕴含是两个不同问题。

---

# 四、支持度必须使用 Full / Partial / None

TREC 2025 RAG Track 的支持评估非常适合直接借鉴。它把回答拆成句子，并判断引用的文档片段对该句属于：

- Full Support；
- Partial Support；
- No Support。

TREC 对 Full Support 的定义是：引用片段支持回答句子中的全部信息；Partial Support 是只支持其中一部分；No Support 是完全不相关或没有支持。它还分别报告 citation precision 和 citation recall。([trec.nist.gov](https://trec.nist.gov/pubs/trec34/papers/Overview_rag.pdf?utm_source=openai))

我建议你的系统使用下面五级标签：

```text
FULL
证据支持主张的全部事实、条件和限定。

PARTIAL
证据只支持主张的一部分，或漏掉关键限定。

CONTRADICT
证据与主张相冲突。

NONE
证据和主张相关性不足，不能支撑。

UNKNOWN
当前文本不足以判断。
```

## 示例

答案写：

> 该软件从 3.4 版本开始支持 PDF 离线导出，Windows 和 Linux 都支持，而且不需要联网。[S1]

引用 S1 的原文是：

> 3.4 版本新增 PDF 导出功能。

那么 S1 对整句话只能判为：

```text
PARTIAL
```

因为 S1 只支持：

```text
3.4 版本
PDF 导出
```

没有支持：

```text
离线
Windows
Linux
不需要联网
```

这正是搜索智能体最常见的错误：前半句被证据支持，后半句是模型自己补出来的。

所以不能因为句子里面有一部分正确，就把整句话判成 FULL。

# 五、Nugget 是评价复杂答案的关键

FActScore 的重要启发是：长答案通常由很多原子事实组成，一个答案可能总体“看起来正确”，但混杂了少量未被支持的信息。因此应该先把回答拆成原子事实，再评估每个事实是否有可靠证据支持。([arxiv.org](https://arxiv.org/abs/2305.14251?utm_source=openai))

## 1. Nugget 的数据结构

建议这样表示：

```json
{
  "nugget_id": "N3",
  "text": "3.4 版本支持 PDF 离线导出",
  "importance": "vital",
  "type": "version_constraint",
  "required_conditions": [
    "对象=某软件",
    "版本=3.4",
    "格式=PDF",
    "模式=离线"
  ],
  "supporting_evidence": ["E7"],
  "contradicting_evidence": ["E9"]
}
```

## 2. Nugget 的重要性分级

```text
vital
漏掉会导致用户无法做出正确判断。

major
重要信息，但不一定直接改变最终结论。

minor
背景、例子或辅助说明。
```

例如“某软件是否支持离线导出”：

```text
是否支持离线导出：vital
从哪个版本支持：vital
Linux 是否支持：major
某用户的使用体验：minor
```

## 3. Nugget 覆盖率

可以定义加权覆盖率：

```text
Nugget Coverage
= Σ importance(n) × matched(n)
  / Σ importance(n)
```

其中：

```text
matched(n) = 1
```

必须同时满足：

- 答案确实提到了 nugget；
- 语义匹配；
- 条件匹配；
- 没有被其他证据反驳。

不能仅仅因为答案里出现了相同关键词，就认为 nugget 已覆盖。

TREC RAG 也采用 nugget assignment 来评估答案的信息覆盖，同时将其与支持度单独评估。([trec.nist.gov](https://trec.nist.gov/pubs/trec34/papers/Overview_rag.pdf?utm_source=openai))

# 六、建议使用四个归因指标

## 1. Citation Precision

回答中给出的引用，有多少真正支持它所附着的陈述：

```text
Citation Precision
= 真正支持所附主张的引用数
  / 答案给出的引用总数
```

例如：

```text
总共给了 10 个引用
其中 7 个真正支持对应句子
Citation Precision = 0.70
```

## 2. Citation Recall

答案中需要证据支持的内容，有多少确实得到了引用：

```text
Citation Recall
= 得到有效引用支持的 citation-worthy nuggets
  / 所有需要引用的 nuggets
```

一个答案可能 citation precision 很高，但 recall 很低：

```text
每个引用都正确
但只引用了 3 个关键事实中的 1 个
```

这仍然不是一个好的答案。

## 3. Nugget Recall

```text
Nugget Recall
= 被答案覆盖的 gold nuggets
  / gold nuggets 总数
```

这衡量“答案有没有讲全”。

## 4. Nugget Precision

```text
Nugget Precision
= 能映射到 gold nuggets 的答案信息单元
  / 答案信息单元总数
```

这衡量模型有没有添加很多题目没有要求、也没有证据支持的内容。

# 七、对支持度使用加权分，但保留原始标签

可以使用：

```text
FULL       = 1.0
PARTIAL    = 0.5
NONE       = 0
CONTRADICT = -1.0
UNKNOWN    = 0
```

定义：

```text
Support Weighted Score
= Σ nugget_weight × support_weight
  / Σ nugget_weight
```

但不能只公布这个平均分。

因为下面两种情况不应该等价：

```text
情况 A：
一个 vital nugget 只有 PARTIAL 支持。

情况 B：
两个 minor nugget 得到 FULL 支持。
```

因此报告必须同时包含：

```text
vital_full_rate
vital_partial_rate
vital_unsupported_rate
major_full_rate
minor_full_rate
```

一个真正可靠的答案，最低门槛应该类似：

```text
所有 vital nuggets 都被覆盖
所有 vital nuggets 至少有一条有效证据
不得存在未解释的 CONTRADICT
不得把 PARTIAL 伪装成 FULL
不得出现高置信度的无证据主张
```

# 八、答案级 Trust Score

如果必须给评委或产品展示一个总分，我建议使用乘法门控，而不是简单加权相加：

```text
Answer Trust Score
= Nugget Coverage
  × Support Weighted Score
  × Source Applicability
  × (1 - Unsupported Claim Rate)
```

例如：

```text
Nugget Coverage = 0.90
Support Score = 0.85
Source Applicability = 0.80
Unsupported Claim Rate = 0.10
```

则：

```text
Trust Score
= 0.90 × 0.85 × 0.80 × 0.90
= 0.551
```

这个分数不会特别高，因为虽然答案覆盖较好，但来源适用性和无证据断言仍有问题。

乘法门控的好处是：

> 不能靠答案写得很完整，掩盖引用不支持；  
> 也不能靠引用很多，掩盖答案漏掉了关键事实。

# 九、来源 Judge 的推荐输出

给来源评判智能体的输入应该是：

```text
用户问题
问题条件
目标主张
来源标题
来源 URL
来源网站
发布时间
页面正文片段
必要的页面上下文
```

它的输出应该是结构化 JSON：

```json
{
  "source_applicability": {
    "identity": "clear",
    "primaryness": "primary",
    "entity_match": "yes",
    "time_match": "yes",
    "version_match": "partial",
    "condition_match": "unknown",
    "independence": "original",
    "reliability_level": "R3"
  },
  "relevance": {
    "label": "direct",
    "score": 3
  },
  "risks": [
    "厂商自述，可能只证明官方声明",
    "未说明 Linux 支持"
  ]
}
```

重要的是：

```text
reliability_level ≠ truth_probability
```

来源 Judge 只能判断：

> 这个来源是否适合承担该类证据。

它不能直接判断：

> 这个来源说的事实一定是真的。

最终事实判断还要结合：

- 其他独立来源；
- 时间；
- 版本；
- 反例；
- 是否存在更正；
- 用户问题的具体条件。

# 十、Claim-Evidence Judge 的推荐输出

对每个主张和证据片段单独评判：

```json
{
  "claim_id": "C1",
  "evidence_id": "E1",
  "support": {
    "label": "PARTIAL",
    "supported_parts": [
      "3.4 版本",
      "PDF 导出"
    ],
    "unsupported_parts": [
      "离线",
      "Windows 和 Linux",
      "不需要联网"
    ],
    "contradicted_parts": [],
    "reason": "原文只描述 3.4 版本新增 PDF 导出，没有说明离线模式、操作系统或网络条件。"
  }
}
```

这比让模型输出一句：

```text
这个来源支持答案。
```

可审计得多。

# 十一、不能只让一个智能体给自己评分

你提出“用智能体作为评判这个来源是否可靠”，这个方向可以用，但要注意评估器本身也会犯错。

建议采用：

```text
规则 + 评判智能体 + 人工校准
```

## 规则层

处理确定性问题：

- URL 是否存在；
- 是否能访问；
- 引用片段是否真实出现在原文；
- 日期是否匹配；
- 页面是否重复；
- 版本号是否一致；
- SearchPro 是否真的返回过该结果。

## Judge 层

处理语义问题：

- 证据是否蕴含主张；
- 是 FULL 还是 PARTIAL；
- 是否存在条件遗漏；
- 两条来源是否真正矛盾；
- 来源是否适合承担该主张。

## 人工层

重点抽检：

- Judge 判为 FULL 的样本；
- Judge 判为 R3 的样本；
- 最终答案高分但人工不信任的样本；
- 证据片段和答案之间存在条件差异的样本；
- PARTIAL/FULL 边界样本；
- 来源互相矛盾的样本。

CAQA 研究显示，现有自动评估器在细粒度归因标签上仍可能表现不佳，尤其容易混淆“支持不足”“矛盾”和“无关”。因此不能把一个 LLM Judge 的输出直接当作绝对真值。([arxiv.org](https://arxiv.org/abs/2401.14640?utm_source=openai))

# 十二、最重要的反事实测试

要判断系统是真的归因，而不是“先生成答案、再找一条看起来相关的引用”，必须做反事实测试。

## 测试一：替换证据

保留同一个答案，替换引用片段：

```text
原支持片段 → 无关片段
原支持片段 → 过时片段
原支持片段 → 反驳片段
```

如果系统仍然判为 FULL，说明支持评判器被答案或来源标题影响。

## 测试二：删除关键证据

删除支持关键 nugget 的片段，重新生成答案。

期待结果：

```text
答案变成未知
或降低置信度
或明确缺少证据
```

如果答案完全不变，说明模型可能没有真正依赖检索证据。

## 测试三：添加反例

加入一条适用条件完全匹配的反例：

```text
官方当前文档：支持
官方旧版本说明：不支持
```

系统应该输出：

```text
部分成立
```

而不是简单输出：

```text
支持
```

## 测试四：条件删减

把引用中关键条件删除：

```text
原文：Windows 3.4 版本支持 PDF 导出
答案：所有系统、所有版本都支持 PDF 导出
```

系统必须识别出：

```text
条件泛化
```

这类测试比单纯看最终答案正确率更能检验归因能力。

# 十四、最终建议的评估看板

你的搜索智能体每次运行应该至少输出：

```json
{
  "source_quality": {
    "r3_rate": 0.65,
    "applicability": 0.82,
    "time_match_rate": 0.90,
    "independent_source_rate": 0.55
  },
  "nugget": {
    "weighted_coverage": 0.88,
    "vital_recall": 1.0,
    "major_recall": 0.75,
    "minor_recall": 0.60
  },
  "attribution": {
    "citation_precision": 0.91,
    "citation_recall": 0.78,
    "full_support_rate": 0.70,
    "partial_support_rate": 0.22,
    "no_support_rate": 0.08
  },
  "answer": {
    "unsupported_claim_rate": 0.05,
    "contradiction_rate": 0.00,
    "abstention_quality": 0.80
  },
  "efficiency": {
    "search_calls": 4,
    "useful_search_rate": 0.75,
    "latency_ms": 5200
  }
}
```

最核心的产品规则应该是：

```text
只要 vital nugget 没有证据，不允许输出完整确定结论。

只要证据只能支持一部分，必须输出“部分支持”。

只要存在未解释的直接反证，不能输出“完全支持”。

只要来源只能证明“某机构声称”，不能把它写成“事实已经被证明”。
```

最终，你要构建的不是“会搜索并生成答案”的系统，而是：

> 一个能够把来源、证据片段、原子主张和答案 nugget 一一对应起来，并且知道哪些内容只被部分支持的搜索智能体。

这套设计直接吸收了 BrowseComp 的“难找但可核验”、LiveBrowseComp 的“防止模型靠记忆验证”、TREC RAG 的 nugget 与 Full/Partial/No Support、FActScore 的原子事实评价，以及 ALCE 的引用质量评估思路。([arxiv.org](https://arxiv.org/abs/2504.12516))

## My request:
我认为这是搜索智能体里非常关键的一层，但它不应该只是给每个网站打一个“可信度分数”。

更合理的是让 Agent 评判：

比如：

```

判断来源是否适用、可靠、及时、独立

```

Source Judge 可以输出：

```json
  "identity": "clear",

  "independence": "original",
```

这里的 `R3` 不应该解释成“真实性 97%”，而应该表示：
```

R2：可靠的二手材料或可交叉验证的来源
R1：相关，但有时间、身份或适用条件问题
R0：只能作为搜索线索
```

```sql
FULL：完整支持
PARTIAL：只支持一部分
CONTRADICT：与主张冲突
NONE：相关但不能支持
UNKNOWN：材料不足以判断
```

```
PARTIAL
```

支持了：

```
离线
Windows
Linux
```
